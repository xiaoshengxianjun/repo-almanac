# 项目志（RepoAlmanac）第一版需求与技术方案

项目志是一款本地桌面工具，面向第一次接手某个代码库的开发者和负责评估改造成本的维护者。用户选择项目文件夹后，应当能回答三个问题：**这个系统有哪些功能，一次用户操作经过哪些代码，准备升级时应先处理什么？** 每个重要结论都可以回到项目中的文件、符号或对应版本的官方资料核对。

## 1. 首版范围

| 用户选择的项目 | 首版提供的能力 |
| --- | --- |
| 任意可读目录，包括没有 Git 历史的项目 | 文件数量、逻辑总大小、文件类型、体积图、目录下钻、路径搜索。根据已知清单和配置识别技术栈，列出无法读取的目录。 |
| JS/TS 项目 | 识别入口、模块导入、可静态解析的函数定义和引用。按子项目展示清单、构建工具和运行时线索。 |
| Vue 3 + Vue Router 4 项目 | 首个完整业务适配器。识别静态路由、页面、模板事件、处理函数以及可解析的 HTTP 请求。同一项目含受支持的 Express 路由时，继续定位服务端处理函数。 |
| 使用 npm 的项目 | 解析直接依赖、锁定版本、运行时约束和插件兼容范围，生成分阶段升级建议。首批框架迁移规则覆盖一个有官方指南、可用样例复现的 Vite 跨主版本场景。 |

Vue 3、Express 和 npm 是建议的首批深度适配对象，便于用一个前后端样例验证全流程。其他项目按已有证据展示文件、技术栈和入口。Vue 2、React、其他后端框架的深度流程适配，待真实旧项目样本确定优先级。首版交付只读分析、源码定位和报告导出；执行升级由维护者在自己的开发流程中完成。

## 2. 用户如何读懂业务和定位代码

### 打开和关闭工作区

首次启动进入空工作区，用户主动选择本地项目目录后开始扫描。点击顶栏左端的「离开项目」图标可结束当前查看并取消进行中的扫描，重启后仍停留在首页。重新选择最近关闭的目录可以恢复上次扫描结果。

### 从业务入口开始

首页先展示子项目、可识别的业务功能、入口和技术栈。功能名称优先取自可解析的菜单文本、路由标题、页面标题和按钮文案，每项保留出处。缺少名称时直接展示路由路径或符号名。README 中的业务说明作为文档证据单列，便于核对描述和当前实现是否一致。

功能按已声明的菜单层级或父子路由分组。例如“订单管理”可展开为“查询订单”和“订单详情”。每个功能列出入口、可触发的动作，以及代码中明确的请求或可见结果。有静态角色守卫时附上访问条件；只有目录名或翻译缺失的文案键时保留原名，供用户核对。没有模型密钥时，使用这些字段直接生成可读摘要。

用户可以搜业务词、页面路径、接口、文件名或函数名。例如搜“提交订单”，结果优先展示文字直接命中的动作和页面，其后列出沿已解析引用找到的请求和处理函数。选择功能后，先看一条操作的步骤列表，再按需展开分支；同一页有“保存草稿”和“提交订单”时，从各自的事件处理函数分别追踪。

### 一次“提交订单”操作如何呈现

以下是用于说明界面和验收的虚构项目。文件名、行号和流程属于样例。

| 用户看到的步骤 | 可点击的项目证据 | 程序如何建立关系 |
| --- | --- | --- |
| 进入结算页 | `apps/web/src/router.ts:12` · `/checkout` | 路由记录将路径映射到可解析的页面组件。 |
| 点击“提交订单” | `apps/web/src/views/Checkout.vue:18` · `@click="submitOrder"` | 将按钮文案、事件及同组件中的处理函数绑定，区分同页其他按钮。 |
| 调用创建订单函数 | `apps/web/src/views/Checkout.vue:46` · `submitOrder` | 在处理函数内找到 `createOrder(cart)`，并解析到导入符号的定义。仅导入函数不足以建立调用关系。 |
| 发起创建订单请求 | `apps/web/src/api/orders.ts:9` · `createOrder` | 读取调用的 HTTP 方法及路径，显示 `POST /api/orders`。 |
| 定位服务端处理函数 | `apps/api/src/routes/orders.ts:14` · 路由注册；`apps/api/src/handlers/orders.ts:21` · `createOrderHandler` | 以服务归属、挂载前缀、路径和 HTTP 方法匹配路由，再沿处理函数引用跳到定义。 |

用户点击任一步，桌面端就打开内置只读源码预览，高亮对应行和符号，同时显示上一步、下一步以及关联依据。支持复制相对路径和行号。若扫描后文件已变更，先提示刷新定位。用户由此可以从业务词直接找到实现，也可以从一个函数反查哪些已识别流程使用了它。

**证据不足时，界面也要给出有用的终点。** 如果服务端在另一个仓库，流程停在可定位的 HTTP 请求；如果多个服务都声明相同接口，展示候选和缺失的服务归属信息；如果只看到创建订单的请求，页面只写“提交创建订单请求”。“订单已支付”“库存已扣减”等结果需要各自的实现证据。

### 文件和体积视图

矩形面积表示文件逻辑字节数。点击目录逐级下钻，用同一筛选条件联动文件表，支持按大小排序、路径搜索和查看零字节文件。默认展示业务文件，按扫描时的依赖、构建及忽略规则筛选。开启「显示非业务文件」会同时更新目录、体积排行、矩形图与清单。普通文件按路径计数，符号链接单列且默认不跟随，读取失败单列。大文件榜用于发现占用来源；网页加载优化还需结合构建产物或实际传输数据。

## 3. 升级建议如何生成

1. **确定现状。** 在各工作区分别读取依赖声明和对应锁文件。区分声明范围、锁定版本和 CI 实际配置的 Node 版本，同时保留文件位置。锁文件缺失、多种锁文件并存或开发与 CI 环境不同，报告标出影响的判断。npm 锁文件按版本结构解析，老项目样本覆盖 v1、v2、v3。[npm 锁文件格式](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/)
2. **建立候选。** 从该包对应的 registry 获取版本元数据，分别列出当前声明范围内的更新及需要评估的跨主版本候选。记录来源、查询时间、目标版本和升级理由。离线时复用标明日期的缓存；缺少元数据时仍能查看本地现状。扫描完成后自动查询可确认公开的 npm 直接依赖。私有源、工作区包和未确认的来源仅在本地展示。最高稳定版与范围内候选均排除预发布及已弃用版本。
3. **判定约束。** 用 `semver` 比对候选的 `engines.node`、已使用插件的 `peerDependencies` 和工作区版本。对支持的框架，再用带适用版本和官方出处的规则匹配配置写法或 API 调用。多项建议按前置依赖排序；构建工具升级关联到它负责构建的子项目，只有能追踪到具体业务流程时才进一步标注页面。[npm 包约束](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/) · [npm semver](https://github.com/npm/node-semver)
4. **输出决策。** 有明确约束冲突时标为**已知阻塞**，关键输入缺失时标为**信息不足**，已检查的条件通过时标为**可试升级**。每项列明现状与目标、收益或动因、证据、覆盖范围、前置条件、改动顺序、验收和回退。报告可以得出“本次范围内没有需要优先处理的升级”。

**同一商城的升级报告样例。** 假设上述前端使用 Vite 4，CI 固定 Node 16。以历史版本 Vite 5.4.0 演示规则，它声明的 Node 范围为 `^18.0.0 || >=20.0.0`。报告可直接判定 CI 环境构成阻塞，并链接 CI 配置和目标包声明。如果项目配置还命中旧版数组形式的 `worker.plugins`，则增加迁移为函数的一步。实施顺序是先记录旧构建和结算流程基线，再验证候选 Node 可以构建旧项目，随后更新 Vite、受影响配置和锁文件。验收包括干净安装、生产构建和结算冒烟测试，使用 Worker 时另测对应路径。失败时恢复本步配置、依赖、锁文件及相应的 CI 环境。示例里的历史版本仅作规则演示。[Vite 5.4.0 运行时约束](https://raw.githubusercontent.com/vitejs/vite/v5.4.0/packages/vite/package.json) · [Vite 4 到 5 的迁移指南](https://v5.vite.dev/guide/migration)

## 4. 技术架构

| 模块 | 首版实现与职责 |
| --- | --- |
| 桌面应用 | Electron 主进程处理系统目录选择、扫描任务和报告保存。React + TypeScript 渲染项目概览、流程、源码、体积和升级视图。渲染进程通过限定的 IPC 接口按需读取结果。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model) |
| 扫描与存储 | Node.js `utilityProcess` 限并发遍历目录，分批写入应用数据目录中的 SQLite。先产出文件元数据，再按子项目深度解析源码。每次扫描使用独立快照，完成后切换；取消或中断时保留上次完整结果。 |
| 源码分析 | 用 TypeScript Compiler API 解析 JS/TS 的语法树、导入和符号；用 `@vue/compiler-sfc` 拆解 Vue 单文件组件，解析模板事件并映射回原文件位置。Vue Router 适配器处理静态嵌套路由和字面量懒加载；Express 适配器处理可解析的挂载前缀和 HTTP 方法。[TypeScript 编译器 API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API) · [Vue 单文件组件](https://vuejs.org/guide/scaling-up/sfc.html) · [Vue Router 嵌套路由](https://router.vuejs.org/guide/essentials/nested-routes.html) · [Express 路由](https://expressjs.com/en/guide/routing/) |
| 查询与展示 | SQLite 保存节点、关系和证据位置，按工作区、路径及符号建立索引。查询从所选动作展开并限制深度，遇到循环保留回链。ECharts 绘制按目录聚合的矩形树图，明细分页；Markdown 导出保留相对路径、行号、快照及规则版本。[ECharts 磁盘体积示例](https://echarts.apache.org/examples/en/editor.html?c=treemap-disk) |
| 升级规则 | TypeScript 规则接收项目事实和版本元数据，输出状态、命中证据和前置条件。每条专用迁移规则随 GitHub 仓库维护适用版本、上游资料、命中样例和反例。 |

### 从代码提取业务关系

- **项目边界。** 先定位根清单、npm workspaces、子项目和入口。按 `tsconfig` 的路径别名和可静态读取的构建别名解析模块。一个前端只和归属明确的后端连接，避免不同子项目的同名函数或同路径 API 串线。
- **结构与行为。** 节点包括路由、页面、操作、函数、HTTP 请求和服务端处理函数。关系明确区分“导入”“绑定事件”“调用”“发送请求”和“处理请求”。默认只沿行为关系展开操作流程；导入关系用于辅助浏览。解析字面量 `fetch`、常见 Axios 方法和可跟踪的本地包装函数。
- **确定性。** 静态可解析的关系标为“有代码证据”；由命名、文档或不完整路径得到的关联标为“候选”；运行时注册、动态 URL、无法归属的网关转发标为“待确认”。源码关系描述可能发生的操作路径；异常分支和条件分支如有证据则标注触发条件。
- **持久化与定位。** 每条关系记录起点、终点、关系类型、解析依据和证据编号。证据保存工作区、相对路径、起止行列、符号、内容指纹和快照编号；版本元数据另存来源及时间。同一套证据支撑流程图、搜索、报告和源码跳转。

### AI 如何参与

基础功能可以在没有模型密钥时完成。用户主动选择“解释此流程”或“生成详细迁移方案”后，再把相关节点、证据编号、选定代码片段和版本匹配的官方迁移资料交给模型。模型负责把步骤讲清、整理改造顺序和回归清单。它提出的业务含义或影响面如无可核对依据，放入“待验证”。

模型输出使用结构化字段，应用校验证据编号、路径、候选版本及规则状态。阻塞状态由规则引擎确定。校验失败或服务不可用时，仍展示同一份规则报告。首版实现一个可配置服务地址的适配器，支持使用同一请求格式的本地模型服务或用户自带密钥的云服务。用户填写的密钥经 Electron safeStorage 处理后保存在本机应用配置里。调用云服务前可预览发送的项目证据。当前版本的存储、传输和清除范围见[隐私说明](../PRIVACY.md)。

### 本机数据与执行边界

只读扫描用户选定目录。静态读取配置，不加载项目脚本、执行安装或运行构建。源码预览按扫描记录和根目录校验路径；公共依赖的版本查询自动进行，外部模型解释需单独确认。扫描索引保存在本机，可按项目清除。扫描进度区分目录遍历、源码解析和规则评估，支持取消；权限错误和解析失败都保留其影响范围。

## 5. 实施顺序与验收

| 里程碑 | 可交付结果 | 验收方法 |
| --- | --- | --- |
| M1 · 项目与文件 | 打开本地目录，形成快照，浏览体积图及文件表 | 用含隐藏文件、空文件、符号链接和无权目录的样本核对数量与字节数。用十万文件样本记录机器配置、首屏反馈、总耗时和峰值内存；扫描中能浏览已有统计并取消。 |
| M2 · 业务与代码 | 支持结算、草稿等操作链，支持业务词搜索、源码跳转和反向查看流程 | 用维护者标注的样本核对每条关系和定位行。覆盖同页双按钮、嵌套路由、路径别名、同名接口和外部服务。已标注的关键步骤可打开正确代码；未消歧的接口不得自动连线。 |
| M3 · 升级 | npm 版本候选、兼容性判断、一个 Vite 迁移规则集、Markdown 报告 | 固定元数据测试可试升级、已知阻塞和信息不足三种结果，覆盖旧锁文件、缺锁、离线和插件冲突。选一条建议由维护者试迁移，核对实际前置条件、构建结果与关键流程回归。 |
| M4 · 桌面发布 | 本地分析、导出与可选 AI 入口，按目标平台提供 GitHub Releases 安装包 | 建议首测 Windows 与 macOS。在干净环境验证选目录、中文路径、只读权限、取消、重扫和导出；无密钥可完成 M1–M3，模拟模型超时后仍能查看报告。 |

**首版用户验收目标。** 给 3 位未参与样例开发的工程师同一个陌生项目，各自独立完成三件事：说清一次提交订单的已识别步骤；打开前端触发点和服务端处理函数；解释升级为何受阻、该先验证什么。建议门槛为至少 2 人在 10 分钟内完成全部任务，结果由项目维护者按预先标注的答案核对。这是待验证的产品目标，样本同时应包含无法完整解析的路径，以检验用户能否识别证据边界。
